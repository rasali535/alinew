## 1. Purpose

Ras Ali Labs (Pty) Ltd systematically reviews application event audit logs from the Ralion backend environment to identify indicators that unauthorized access to Meta Platform Data may have occurred or been attempted.

The primary objective of this policy is to enforce proactive threat detection, anomaly identification, and rapid forensic investigation across authentication, access control, credential management, webhook processing, and data transmission workflows.

---

## 2. Scope

This policy applies to all application event audit logs generated by Ralion backend services that store, process, or transmit Meta Platform Data, including:

* **Authentication & Session Events:** User login outcomes, multi-factor factor enrollments, and session revocations (`AUTH_LOGIN`, `AUTH_LOGIN_FAILED`, `MFA_ENABLED`).
* **Access-Control & RBAC Operations:** Role changes, permission updates, and tenant isolation events (`ROLE_CHANGED`, `PERMISSION_GRANTED`).
* **OAuth & Credential Lifecycle Events:** Token creation, long-lived token exchange, permission revocation, and account disconnection (`META_CONNECT`, `META_TOKEN_CREATED`, `META_TOKEN_REVOKED`, `META_DISCONNECT`).
* **Inbound Webhook Verification:** HMAC-SHA256 signature verification outcomes and delivery intake.
* **Graph API & Data Access Operations:** Outbound Meta Graph API requests, response status tracking, and error handling (`META_API_REQUEST`, `META_API_FAILURE`).
* **Meta Data Deletion Execution:** Signed user data deletion callbacks (`POST /api/meta/data-deletion`) per Meta Platform Term 4.a.
* **Threat Tripwires & Security Alerts:** Brute-force tripwires, CSRF nonce validation failures, and suspicious rate limit violations (`SECURITY_ALERT`).

## 3. Mandatory 7-Day Review Requirement

> ### 📅 MANDATORY POLICY REQUIREMENT: 7-DAY AUDIT LOG REVIEW
> **Ras Ali Labs shall review application event audit logs from the Ralion backend environment at least once every 7 days.**

The review process operates through a combination of **continuous automated monitoring** and a **mandatory weekly manual security audit** conducted by authorized security personnel.

Every completed weekly review must be formally recorded in the database table `public.security_review_records` and retained for compliance verification.

---

## 4. In-Scope Indicators of Unauthorized Access

> ### 🔍 MANDATORY THREAT INDICATOR COVERAGE
> **The log-review process must evaluate logs against four primary threat indicators:**
> 1. **Unauthorized or Anomalous Authentication Activity**
> 2. **Access-Control Failures and Privilege Escalation**
> 3. **Signs of Application Exploitation or Abuse**
> 4. **Unusual Data Access or Extraction Patterns**

### 4.1 Unauthorized or Anomalous Authentication Activity
The review inspects logs for:
* Repeated failed authentication attempts ($\ge 5$ consecutive failures) indicating potential brute-force attacks.
* Unusual geographic or IP address shifts during administrator logins.
* Authentication attempts against locked or disabled accounts.
* Anomalous OAuth token creation patterns or sudden spikes in authorization code exchanges.

### 4.2 Access-Control Failures and Privilege Escalation
The review inspects logs for:
* Repeated authorization or permission-denied errors against restricted database tables (`social_credentials`).
* Attempts to query data across tenant boundaries (violating PostgreSQL Row Level Security).
* Unexpected or unauthorized administrative role assignments (`ROLE_CHANGED`).
* Unauthorized attempts to bypass token vault access restrictions.

### 4.3 Application Exploitation or Abuse
The review inspects logs for:
* Inbound webhook requests with invalid or missing HMAC-SHA256 signatures (`X-Hub-Signature-256`).
* Repeated OAuth state parameter mismatches indicating potential Cross-Site Request Forgery (CSRF) attempts.
* Sudden spikes in API request volume triggering exponential backoff rate limits.
* Input boundary violations or malicious payload structures targeting server API routes.

### 4.4 Unusual Data Access or Extraction Patterns
The review inspects logs for:
* Abnormal volume of Graph API queries or profile synchronization requests.
* Repeated API failures followed by abnormal success patterns.
* Anomalous bulk exports or automated scraping attempts.
* Disconnect requests originating from unrecognized IP addresses.

## 5. Review Methodology & Operational Architecture

The Ralion audit log review framework operates across two synchronized layers:

```text
┌─────────────────────────────────────────────────────────────────────────────┐
│                    RALION SECURITY MONITORING FRAMEWORK                     │
├──────────────────────────────────────┬──────────────────────────────────────┤
│ 1. Continuous Automated Monitoring   │ 2. Weekly 7-Day Audit Review         │
│    (Real-Time Threat Detection)      │    (Formal Reviewer Verification)    │
│ • `SecurityMonitorService` Tripwires │ • Admin Security Center UI Review    │
│ • Failed Login Threshold Alerts      │ • Weekly Review Record Sign-Off      │
│ • Webhook HMAC Signature Monitoring  │ • Saved to `security_review_records` │
│ • Automated Alert Log Generation     │ • Retained for Meta Compliance       │
└──────────────────────────────────────┴──────────────────────────────────────┘
```

### Review Procedure:
1. **Filter & Inspect:** The security reviewer accesses the Admin Security Center (`/enterprise/security`) and filters `public.security_audit_logs` over the preceding 7-day window.
2. **Examine Key Fields:** The reviewer verifies the **Meta User ID**, **Event Type**, **Date/Time**, and **Success/Failure status** for all recorded events.
3. **Analyze Anomalies:** Any failed authorization, repeated failed login, or signature rejection is cross-referenced with related session logs.
4. **Log Review Sign-Off:** The reviewer submits a formal record into `public.security_review_records` capturing review date, findings count, unremediated threats, and compliance status.

## 6. Risk Triage & Classification

Identified log events are triaged according to security risk:

| Classification | Definition | Action Required |
| :--- | :--- | :--- |
| **Benign / Expected** | Routine operational events (e.g. user-initiated disconnect, expected rate limiting). | Documented as normal system activity. |
| **Suspicious / Unconfirmed** | Isolated signature failures, single-instance authorization errors. | Monitored for recurrence over 24 hours. |
| **Likely Security Incident** | Repeated brute-force attempts, cross-tenant access attempts. | Immediate containment and developer investigation. |
| **Confirmed Unauthorized Access** | Verified unauthorized credential extraction or Platform Data breach. | Full incident escalation under Incident Response Policy. |

---

## 7. Investigation and Incident Escalation

When suspicious activity involving Meta Platform Data is detected during the weekly review:
1. **Initiate Incident Response:** Follow the procedures in [`docs/security/incident-response-policy.md`](file:///c:/Users/Ras%20Ali%20Labs/Desktop/rasalilabs/alinew/docs/security/incident-response-policy.md).
2. **Containment:** Immediately revoke affected OAuth tokens via Graph API (`DELETE /me/permissions`), shred database credentials, and terminate active sessions.
3. **Forensic Audit:** Trace all related `security_audit_logs` entries using correlation IDs and IP addresses to determine the exact scope and duration of unauthorized access.
4. **Remediation & Notification:** Apply necessary code or infrastructure patches and comply with applicable platform and regulatory notification requirements.

---

## 8. Protection of Audit Log Data

* **Credential Redaction:** The audit review interface displays sanitized metadata (`sanitizeMetadata()`). Plaintext tokens, App Secrets, passwords, and encryption keys are never displayed or exposed during reviews.
* **Immutability:** Audit records in `security_audit_logs` are protected by PostgreSQL RLS against modification or deletion.

---

## 9. Review Evidence Retention

Ras Ali Labs maintains complete evidence of weekly review activities:
* **Database Review Records:** Stored in `public.security_review_records` containing reviewer ID, review timestamp, findings, and remediation status.
* **Compliance Retention:** Review records and corresponding audit logs are retained for at least **1 year (365 days)** per the **Log Retention Policy** ([`docs/security/log-retention-policy.md`](file:///c:/Users/Ras%20Ali%20Labs/Desktop/rasalilabs/alinew/docs/security/log-retention-policy.md)).
